## はじめに

先日、ある大先輩から「システムアーキテクトの思考法」について講義していただく機会がありました。そのなかで印象に残ったのがこの言葉です。

> 「良いアーキテクチャ設計とは、全てで満点を取れるものではなく、生じる副作用が許容範囲であり、その理由を全て説明できる設計である」

思い返すと、昔のプロジェクトで技術選定を担当したことがありますが、時間をかけて調べ、議論を重ねて決定にこぎつけて、あんなに大変な思いをしたのに、今となっては「どう悩んだか」をほとんど覚えていません。コードは残っていても、「なぜこうなったか」は残していませんでした。

個人ブログの技術スタックを選定するにあたり、今回はADRを書いてみることにしました。個人開発でADRを書くのは大げさかもしれませんが、AIコーディング全盛の今、「なぜこうしたか」が残っていると将来のコンテキスト補完にも役立ちそうです。

## ADRとは

ADR（Architectural Decision Record）とは、アーキテクチャに関する意思決定を記録するドキュメントです。

重要なのは「意思決定の記録」という部分です。「Astroを採用した」という事実だけなら、コードを読めばわかります。残すべきは「なぜ」——どんな課題があり、どんな選択肢を検討し、それぞれのトレードオフは何で、なぜその決定に至ったのか、という過程です。

「アーキテクチャに解はない」というのも大先輩の言葉ですが、まさにこれで、解がないからこそ「なぜこの解を選んだか」について説明責任が生じます。ADRはその記録です。

## テンプレートはMADR ミニマルにした

ADRには公式のフォーマットがなく、様々な人が独自のテンプレートを提案しています。代表的なものに[Nygard ADR](https://github.com/architecture-decision-record/architecture-decision-record/blob/main/locales/en/templates/decision-record-template-by-michael-nygard/index.md)・[Y-Statement](https://medium.com/olzzio/y-statements-10eb07b5a177)・[MADR](https://github.com/adr/madr/blob/4.0.0/template/adr-template.md?plain=1)などがあります。今回はMADR（Markdown Architectural Decision Records）の[最小版](https://github.com/adr/madr/blob/4.0.0/template/adr-template-minimal.md?plain=1)を使いました。

MADRは[Olaf Zimmermann](https://ozimmer.ch)と[Oliver Kopp](https://github.com/koppor)が設計したテンプレートで、[adr.github.io](https://adr.github.io/)で公開されています。フル版とミニマル版があり、ミニマル版は次の流れで構成されています。

```
コンテキストと問題提起 → 検討した選択肢 → 決定の結果 → 結果・影響 → 追加情報（任意）
```

フル版には`deciders`（決定者）・`consulted`（相談した人）・`informed`（報告した人）といったメタデータや「確認（検証）」セクションがありますが、チーム開発で真価を発揮するフィールドなので、一人で書くときは不要です。まずミニマル版から始めて、必要になったら足していくのがちょうど良いと思いました。

## 書くべきことと避けるべきパターン

テンプレートの形式を守るだけでは不十分で、内容にも気をつけるべき点があります。アンチパターンについては[How to create Architectural Decision Records (ADRs) — and how not to](https://ozimmer.ch/practices/2023/04/03/ADRCreation.html)に詳しいです。


### Badを正直に書く

ADRの「結果・影響」には悪い点も書く必要があります。良い点しか書かれていないADRは「Fairy Tale：おとぎ話」と呼ばれるアンチパターンです。

例として、次のようなADRは不十分です。

> 例：「イベントベースアーキテクチャを選択した。なぜなら通信参加者を疎結合にするからだ。」

「設計・実装・テストの追加工数は？」「イベントスキーマ定義が受信者を送信者に結合するのでは？」という観点が抜けています。Badを書くのは自己批判ではなく、トレードオフを把握していることを示しています。

### 代替案は実質的に比較できるものを挙げる

「独自のRDBMSを実装する」を代替案として並べるのはアンチパターン（Dummy Alternative：ダミーの代替案）です。実際に選べる選択肢を挙げることに意味があります。「選んだ結論を正当化するためのダミー」を置いても、ADRの価値はありません。

## 実際に書いてみた

以上を踏まえて書いたADRがこちらです。

```markdown
# 個人ブログの SSG・UI フレームワーク・スタイリングを選定する

* Status: accepted
* Date: 2026-06-23

## コンテキストと問題提起

静的ホスティングで運用することは [20260623_adopt_static_hosting.md](20260623_adopt_static_hosting.md) で決定済み。本 ADR はその前提のもと、SSG・UI フレームワーク・スタイリングの技術スタックを選定する。

コンテンツ配信を主目的とした静的サイトであり、想定するインタラクティブ機能は限定的（ダークモード・目次・検索・コードコピー）。クライアントサイド JavaScript を最小化しながら技術学習の場としても活用したい。

**この決定が答える問い：** クライアントサイド JavaScript を最小化しつつ限定的なインタラクティブ機能を実現できる技術スタックはどれか？

## 検討した選択肢

* Astro + Svelte + Panda CSS
* Astro + React + Tailwind CSS
* Next.js

## 決定の結果

選択肢：**Astro + Svelte + Panda CSS**、なぜなら Astro はデフォルトで全ページをゼロJS出力し、Islands としてマークしたコンポーネントのみをハイドレーションする設計であり、「静的ページを基本としつつ必要箇所のみインタラクティブにする」という本プロジェクトの方針と設計思想が一致するからである。また、Svelte のコンパイル時最適化と Panda CSS のビルド時 CSS 生成により、クライアントサイドの実行コストを最小化できる。Astro + React + Tailwind CSS は同じ Astro ベースだが既存知識の延長になるため学習目的を果たせない。Next.js は静的エクスポートも可能だがコンテンツ主体のサイトには機能過多。

### 結果・影響

* Good: Islands Architecture により、静的ページとして出力しながら必要箇所だけインタラクティブにできる
* Good: Markdown + Content Collections による Git ベースのコンテンツ管理
* Good: Svelte のコンパイル時最適化と Panda CSS のビルド時 CSS 生成によりランタイムコストがほぼゼロ
* Good: Panda CSS により TypeScript でデザイントークンを管理でき、型安全なスタイリングを実現できる
* Good: Svelte という未経験スタックを実プロジェクトで習得できる
* Bad: Svelte は未経験のため初期開発速度が低下する可能性がある
* Bad: Panda CSS は比較的マイナーフレームワークであり、長期的なメンテナンス継続が不透明である
* Bad: React + Tailwind と比べてコミュニティ規模が小さく、サンプルコードや Q&A が少ない

## 追加情報

* WordPress は Git によるコンテンツ管理および DB 不要という要件の時点で除外した
* Gatsby は React + GraphQL を前提とするアーキテクチャが小規模サイトに対して複雑すぎるため除外した
* スタイリングは Tailwind CSS・CSS Modules・SCSS も検討したが、TypeScript によるデザイントークン管理と型安全性を優先して Panda CSS を選択した
* UI フレームワークは Astro + Vue も検討したが、既存知識の延長ではなく新規学習を優先した
* インタラクティブ機能の要件が大きく変わった場合、または Panda CSS の学習コストが許容範囲を超えた場合は本 ADR を再検討する

```

### 書いてみてわかったこと

書いてみてわかったのは、代替案を「なぜ選ばなかったか」だけで評価するのはアンフェアだということです。Next.jsには「豊富なエコシステム」というれっきとしたメリットがある。それを認めたうえで「今回の要件には合わない」と書く方が、決定の根拠として説得力があります。

## どの決定をADRにするか

ADRを知ると「全部書かなければ」という気持ちになりますが、["Everything is an ADR"](https://techleadjournal.dev/episodes/113/)というアンチパターンがあります。[Michael Keeling](https://github.com/michaelkeeling)が命名したもので、些細な決定まで全部ADRにすると記録が溢れ、本当に重要なものが埋もれてしまいます。

判断の軸は「アーキテクチャ上の重要性」があるかどうかです。次のいずれかに当てはまる決定はADRの候補になります。

- 取り消しにコストがかかる（DBの選定、フレームワークの選定など）
- 複数のコンポーネントや将来の開発に影響する（横断的関心事）
- 「なぜこうしたのか」と聞かれる可能性がある
- 初めて採用するアーキテクチャパターンや技術
- 過去に痛い目を見た類の決定

逆に言えば、誰でも5分で同じ結論に至るような決定や、すぐに変更できてコストがほぼゼロなものはADRにしなくていいです。変数名をどうするかはADRではなくコードレビューでやることです。

## ADRは書き直さない

承認・却下されたADRはイミュータブル（不変）です。後から「やっぱり違った」となっても、元のADRを書き直したり削除したりしてはいけません。

代わりに、新しいADRを書いて古い方のステータスを `superseded by ADR-XXX`（ADR-XXXに置き換えられた）とします。こうすることで「いつ・なぜ方針が変わったか」の変遷が追跡できます。

過去の判断が間違いだったとしても、その事実は記録として残す。意思決定の歴史がそのまま学習記録になる、という考え方です。

## おわりに

実際に書いてみると、「なぜこの技術を選んだか」を改めて言語化する作業になりました。なんとなくで決めていたわけではないのに、いざ文章にしようとすると曖昧な部分が浮かび上がってきます。

書き終えてみると、大先輩の「説明責任」という言葉の意味が少しわかった気がしました。決定の根拠を言葉にすることで、自分の判断を改めて検証することになるのかもしれません。

個人開発ではありますが、「半年後の自分に説明できるか」という問いかけとして有用なものになったと思います。
